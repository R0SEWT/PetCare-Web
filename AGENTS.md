# Repository Guidelines

## Project Structure & Module Organization
This is a TanStack Start + Vite React project written in TypeScript. Application code lives in `src/`. Routes are file-based in `src/routes`; keep `src/routes/__root.tsx` as the root shell and do not edit `src/routeTree.gen.ts` manually because it is generated by the router plugin. Shared UI components live in `src/components`, with shadcn-style primitives in `src/components/ui`. Shared hooks are in `src/hooks`, utilities and server helpers are in `src/lib`, global styles are in `src/styles.css`, and static/public assets belong in `public` or `src/assets` depending on how they are imported.

## Build, Test, and Development Commands
Use Bun for local dependency and script execution because this repo includes `bun.lock`.

- `bun install`: install dependencies.
- `bun run dev`: start the Vite development server.
- `bun run build`: create a production build.
- `bun run build:dev`: build with development mode settings.
- `bun run preview`: preview the built app locally.
- `bun run lint`: run ESLint across the repository.
- `bun run format`: run Prettier over the repository.

## Coding Style & Naming Conventions
Use TypeScript and React function components. Prefer the `@/` alias for imports from `src`, matching `tsconfig.json` and `components.json`. Follow Prettier formatting and ESLint rules; use 2-space indentation after formatting. Keep route filenames aligned with TanStack routing conventions, for example `index.tsx`, `dashboard.pets.$petId.tsx`, and `__root.tsx`. Use `.server.ts` for server-only modules instead of Next.js `server-only`.

## Testing Guidelines
No test framework, test script, or coverage threshold is currently configured. When adding tests, colocate them near the code under test using `*.test.ts` or `*.test.tsx`, add the required test runner script to `package.json`, and document any coverage expectation in the same change. Until then, verify changes with `bun run lint` and the smallest relevant build command.

## Commit & Pull Request Guidelines
The current Git history contains a single snapshot-style commit, `PetCare Demo V1`, so no strict commit convention is established. Use concise, descriptive commit subjects that identify the changed area, such as `Update dashboard pet details`. Pull requests should include a short summary, linked issue when applicable, verification commands run, and screenshots or screen recordings for visible UI changes.

## Security & Configuration Tips
Do not commit secrets, tokens, local credentials, or machine-specific configuration. Keep environment-specific access in local ignored files or deployment configuration, and avoid reading or exposing secret contents during audits.

## Project-Kit Adaptation
This repository uses the local `project-kit` workflow in a Bun/TanStack form. Keep project-kit Python/data defaults out of this app unless a real Python service is added. Track durable work with `bd`, use `.github/workflows/ci.yml` as the required quality gate, and prefer pull requests for changes to `main`.

## Session Close (PR flow — project-kit adaptation)

If a remote and branch-protection rules are configured, merge only after CI is green and review conversations are resolved.
